# ADR-0005：Markdown 表格 —— 从「刻意不解析」改为「解析并原生渲染」

- 状态：**已推翻原案**（决策本身有效，但它**推翻了同一文件里的前一个决策**；前案原文保留于下）
- 日期：2026-10-15

## 背景

`core/MarkdownLite.ts` 建立时明确写了「**三条刻意的不做**」，第 1 条就是：

> **不解析表格**。手机上没有可读的宽表格；源工程自己的 `HtmlStructurePreview`
> 也明确「刻意不画表格」，口径一致。

该决策在**静态预期**下是合理的：窄屏表格体验差，且源工程有先例。

但真机实测推翻了这个预期——用户反馈「会话页中的 MD 渲染问题很大，
**尤其表格类**」。dump 证据显示：一张表格被整体当成**单块 `Text` 裸渲染**，
节点文本直接是 `| 坑 | 说明 |\n|---|---|\n| 证书类型...`，屏幕上是一根根竖线的原始文本；
链接 `[signing/...](...)` 同样整串照登。

**根因不是"表格不好看"，而是"有没有人处理它"**：不解析 → 落进 PARAGRAPH 分支 →
被 `inlineMarkup` 剥掉标记后原样输出。用户看到的是**未处理的源码**，
比"排版欠佳"严重得多。而 `HtmlStructurePreview` 的先例并不可比——
它面对的是用户工作区里的 HTML **文件**，本工程面对的是助手**正文**。

## 决策

**解析 GFM 表格与分隔线，并提供原生表格渲染。** 具体：

1. `MdBlockKind` 新增 `TABLE` / `HR`；
2. 表格以「表头 + 分隔行 + 数据行」解析，**硬闸门是下一行必须是分隔行**
   （避免把 `a | b` 这类命令行管道正文吃掉）；
3. 渲染层套横向 `Scroll`，表头浅底 + 分割线，列宽按内容估算（夹在 64–240vp）；
4. 先过 `inlineMarkup` 再估算列宽（否则长链接会把列宽顶到上限）；
5. 顺带补行内标记：链接、图片、删除线、星号斜体
   —— **刻意不认下划线系**（`a_b_c`、`__init__` 会被正则吃坏）。

## 理由

- 前案的**前提被实测否证**：真实会话里表格确实存在，且"不解析"的后果不是"简朴"
  而是"显示源码"。
- 源工程用第三方库 `com.mikepenz.markdown.m3` 渲染，**它本身支持表格**——
  口径其实一致，只是我们当初误以为它不画表格（那句话针对的是 HTML 预览，不是 Markdown）。

## 后果

- **收益**：表格、分隔线、链接、行内样式全部转为正确的原生渲染；新增 19 条用例。
- **代价**：表格列宽估算成了新的坑源——见 ADR-0005 后继的坑 23
  （西文字宽系数贴边导致 `bundleName` 被断成 `bundleNam` / `e`）。
  **估算类代码天然贴边，宁可略宽也不断词**；这是本决策引出的、需要单独盯的一类风险。
- **教训（写给后来者）**：`MarkdownLite.ts` 文件头那句「刻意的不做」还在，
  但**表格已不在其列**——改口径时必须同步改注释，否则文档会继续传播已被推翻的结论。

## 附：被推翻的原案（原文保留）

> ## 三条刻意的不做
>
> 1. **不解析表格**。手机上没有可读的宽表格；源工程自己的 `HtmlStructurePreview`
>    也明确「刻意不画表格」，口径一致。
> 2. **段落内不把换行并成空格**（CommonMark 的软换行规则）。用户写中文时常一行一句、
>    行间不留空行，并成空格会在中文里插出多余空格。保留原换行更贴近他打出来的样子。
> 3. **不做嵌套**（列表里套列表、引用里套列表）。目前真实会话里没有这种形态，
>    猜错了反而会把层级拍平得更难看。

第 2、3 条**仍然有效**，未被推翻。
