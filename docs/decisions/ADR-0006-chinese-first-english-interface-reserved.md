# ADR-0006：中文为主，英文接口预留

- 状态：已采纳
- 日期：2026-10-15

## 背景

用户在移植开始时即明确：**「默认中文，预留英文接口」**。同时要求主题跟随系统。

## 决策

1. 界面文案默认中文，资源同时存在 `base`（中文）与 `en_US` 两套 `string.json`；
2. 所有文案走资源键，**不硬编码字符串**，英文侧留好键位但可暂不完善；
3. 主题不设应用内开关，**跟随系统深浅色**；
4. 遇到"本移植版没有对应能力"的设置项，**保留开关并在页面写明**，不隐藏。

## 理由

1. **预留而非实现**：英文接口留好，将来加英文只需补 `en_US` 的 value，
   不必回头重构取文案的方式。成本最低的做法就是**现在就全部走资源键**。
2. **跟随系统**：手机上"应用内主题开关"会与系统设置打架，用户要求的就是跟随，
   这也省掉一套主题状态管理。
3. **"不许沉默"**：隐藏一个设置项会让用户以为是手机版的缺陷
   （「电脑端有这个设置、手机上没有」）。显式说明是把**能力的边界**交给用户判断。

## 后果

- **代价**：两套资源必须保持键集一致。曾因构建工具写坏 `en_US/string.json`
  而不得不按"抢救骨架再补缺"的脚本法修复（见 `PORT-MAP.md` 坑 8）——
  **改资源文件后必须立刻做二次校验（键数 + 键集 + 顺序）**。
- **代价**：`useWebChat` 这类开关的说明文案也要走资源键，不能图省事写死中文。
- **收益**：测试里可以断言「英文列完整性」（逐 key 断言 `(key,'en') !== (key,'zh')`），
  防止某条英文漏配后**静默回退中文**——这类回归肉眼看不出来。
